# nananeko-status

株式会社ななねこ の稼働状況・メンテナンス告知ページ（https://status.nananeko.co.jp/）。

## なぜ別リポジトリ・別ホストなのか

`nananeko.co.jp` / DeDn / YOYAKUTO / nana-ops は**同一の GCP VM**（`multi-secoundary-host01`,
外部 IP `34.104.174.135`）に同居している。VM 再起動や OS 更新を伴う「重メンテ」では
コーポレートサイトも一緒に落ちるため、**告知の正本を同居ホストに置くことはできない**。

さらに、告知の正本は Web である必要がある。**延長・中止が起きたときに更新して伝えられるのは
Web だけ**だから（メールと X は撤回できない）。

∴ このページは GitHub Pages でホストする。

> ⚠️ **`status.nananeko.co.jp` の DNS を `34.104.174.135` へ向けてはならない。**
> 向けた瞬間にこのページは同居ホストと運命を共にし、存在意義が消える。

## 構成

| | |
|---|---|
| ホスティング | GitHub Pages（このリポジトリの `main` ブランチ / ルート） |
| 独自ドメイン | `status.nananeko.co.jp`（`CNAME` ファイルで指定） |
| DNS | GMO系（`01〜04.dnsv.jp`）に CNAME を1本。ゾーン移管は不要 |
| 依存 | **なし**。`index.html` 1枚。外部 CSS / JS / 画像を読み込まない |

外部リソースを読み込まないのは意図的な制約。本体が落ちている場面で読まれるページなので、
落ちうる先への依存を1つも作らない。

## 状態は「時刻から自動で」決まる

このページの要点。`index.html` の `NOTICES` に **開始時刻と終了予定時刻**を書いておくと、
表示は閲覧時刻と比べて自動的に切り替わる。**計画どおり進んでいる限り、当日の更新作業は無い。**

| 条件 | 表示 |
|---|---|
| `startAt` より前 | 予告 |
| `startAt` 〜 `endAt` | 実施中 |
| `endAt` を過ぎた、かつ `recoveredAt` が空 | **終了予定時刻を過ぎています** |
| `recoveredAt` に時刻が入っている | 復旧 |
| `kind: "障害"` | 障害 |

3行目が重要。**終了予定を過ぎても自動で「復旧」にはしない。**
深夜の作業が長引き、誰もページを更新できなかった場合でも、
ページが「復旧しました」と嘘をつかないようにしてある。この場合はお詫びの一文も自動で表示される。

「サービス別の状況」の表と、ページ最上部の総合ステータスも `NOTICES` から**導出**される。
二重管理する箇所は無い。

### なぜ自動化をここで止めているか

nana-ops による自動更新は「予告の掲載」「障害の掲載」までは可能だが、
**nana-ops 自身が同居ホスト上で動いているため、重メンテ中は nana-ops も落ちている。**
∴ 「延長した」ことを nana-ops から書き込むことは原理的にできない。

延長は、まさに全部が落ちている最中に起きる。だから
**延長の理由と新しい見込み時刻だけは、ホストに依存しない経路（人が GitHub web UI から）で更新する。**
時刻による自動遷移は、その手作業をこの1点にまで減らすための仕組み。

## 更新のしかた

`index.html` の `▼▼▼ ここから編集 ▼▼▼` 〜 `▲▲▲ ここまで編集 ▲▲▲` の間だけを編集する。
**GitHub の web 画面から編集できる**ので、スマートフォンでも更新できる。
コミットすると1分ほどで反映される。深夜の延長対応はこの経路を想定している。

### 通常の流れ

| いつ | 操作 |
|---|---|
| 枠が決まったら | `NOTICES` に1件追加（`startAt` / `endAt` / `impact` を書く） |
| 7日前 | **操作不要** — 自動で「今後の予定」から「予告」カードへ昇格する |
| 開始時 | **操作不要**（自動で「実施中」になる） |
| 終了時 | `recoveredAt` に実際に終わった時刻を入れる |

`NOTICE_LEAD_DAYS`（既定 7）より先の予定は、大きなカードにせず
「定期メンテナンスについて」の**今後の予定**に日付だけ並ぶ。
先の予定を何件登録してもページが散らからないので、枠が決まった時点でまとめて入れてよい。

### サービスの粒度

`SERVICES` は**管理画面と公開サイトを分けている**。通常メンテで止まるのは管理画面だけで、
お客さまが公開したホームページと予約の受付は動き続けるため。
1行にまとめると「自分のホームページが落ちた」と誤読され、実害が出る。

`impact` はサービスごとに書き分けられる:

```js
impact: {
  "DeDn（管理画面）": "…ログインできません。公開しているホームページは通常どおり…",
  "YOYAKUTO（店舗管理画面）": "…ログインできません。予約の受付は通常どおり継続します。",
}
```

この文はサービス別の状況表にもそのまま出る。

### 告知経路（DeDn #1841 / nana-ops #236 の決定）

| 種別 | 経路 |
|---|---|
| 定期メンテ（月2回） | **このページのみ**。メール・X は出さない（月2回のメールは重メンテの開封率を下げるため） |
| 重メンテ・枠超過 | メール + X + このページ |

### 延長したとき ← ここだけは必ず手で

1. `recoveredAt` は **空のままにする**（入れると「復旧」になってしまう）
2. `updates` に理由と新しい見込み時刻を追記する

```js
updates: [
  { at: "2026-09-14 03:40", text: "データの移行に時間がかかっているため、終了予定を 7:00 に延長します。" },
],
```

追記が間に合わなくても、ページは自動で「終了予定時刻を過ぎています」と表示している。

### 障害のとき

`NOTICES` に `kind: "障害"` で追加する。総合ステータスは自動で赤表示に切り替わる。
復旧したら `recoveredAt` に時刻を入れる。

### 後片付け

終わったお知らせは1か月ほど残してから `NOTICES` から削除する。

## セットアップ（初回のみ）

1. このリポジトリを **public** で作成（public なら GitHub Pages は無料）
2. Settings → Pages → Source: `Deploy from a branch` / Branch: `main` / `/ (root)`
3. DNS に CNAME を追加:
   ```
   status.nananeko.co.jp.  CNAME  nananeko-minami.github.io.
   ```
4. Settings → Pages → Custom domain に `status.nananeko.co.jp`
5. DNS 伝播後、**Enforce HTTPS** にチェック
6. 検証:
   ```bash
   dig +short status.nananeko.co.jp        # 34.104.174.135 でないこと ← 最重要
   curl -sI https://status.nananeko.co.jp/ # 200
   ```

## 文面の方針

DeDn の想定利用者は IT に詳しくない中小・零細企業の経営者。そのため:

- 専門用語を使わない（「デグレード」「縮退運転」等は書かない）
- **お客さまから見て何ができなくなるのか**を `impact` に必ず書く
- データが消えないなら「消えません」と明記する（一番の不安がそこなので）
- 本文の文字を大きめに取っている（CSS の `font-size` を小さくしない）

## 既知の制約

- 状態の判定に**閲覧者の端末の時計**を使う。時計が大きくずれている端末では表示もずれる。
  日本時間の扱いは `Asia/Tokyo` 固定なので、閲覧者のタイムゾーンには依存しない。
- ページを開いたままにしても自動では切り替わらない（再読み込みで反映される）。
